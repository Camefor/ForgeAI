## 背景

> **填写指南**：说明做出决策时的处境：当前阶段、团队规模、可用预算、运维能力、时间压力、未来演进预期。背景应提供足够信息让未来的读者理解「当时的约束」。

- 项目处于早期阶段（MVP 或 v0.x）。
- 团队规模小，运维资源有限。
- 域边界尚未完全稳定，拆微服务为时过早。
- 未来存在横向扩展需要，但近期不是瓶颈。

## 决策

> **填写指南**：清晰的决策陈述，一句话可读。避免用「我们认为可能……」等含糊语气。

采用**模块化单体**（Modular Monolith）作为 v0.x 阶段的主架构：

- 单一部署单元，包含 Web / Application / Domain / Infrastructure 分层。
- 内部按业务模块划分明确的模块边界，模块间不直接访问实现，仅通过稳定的内部接口通信。
- 保留未来将模块拆分为独立服务的能力（接口化、异步化、数据所有权清晰）。

## 影响

> **填写指南**：决策带来的正面影响、负面影响、需要承担的技术债。应覆盖性能、可维护性、团队协作、成本、风险等维度。

### 正面

- 单一部署降低运维复杂度与成本。
- 本地开发无需启动多服务，调试与测试简单。
- 跨模块重构在同一仓库完成，不涉及分布式事务。

### 负面

- 单体规模增长到一定程度会出现构建变慢、变更阻塞。
- 不同模块的扩容需求无法独立满足（整体水位决定）。
- 若模块边界腐化（跨模块直接访问内部实现），后续拆分成本陡增。

### 需要配套的实践

- 代码评审强制检查模块边界。
- 关键接口打标（`<module-boundary>`）在 Linter / Analyzer 中拦截违规依赖。
- 关键模块保留"可异步化"接口，方便未来拆分。

## 替代方案

> **填写指南**：列出被评估但未采纳的方案，以及未采纳的具体原因。防止下次重新讨论时信息丢失。

### 方案 A：从一开始就微服务

- **优点**：模块天然边界清晰，可独立扩容。
- **未采纳原因**：早期域边界不稳，运维成本陡增，团队规模不匹配。

### 方案 B：单一大单体，不做模块化

- **优点**：开发最快。
- **未采纳原因**：中期无法演进，重构成本高，核心模块强耦合。

### 方案 C：Serverless 函数化

- **优点**：按需伸缩，零运维。
- **未采纳原因**：业务流程有状态与跨步骤事务，函数化会引入大量粘合层。
