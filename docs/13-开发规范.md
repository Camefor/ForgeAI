## 5. 注释与文档

> **填写指南**：注释解释「为什么」而非「是什么」；核心业务逻辑必须有注释；简单赋值和明显 CRUD 不添加无效注释。公共 API 使用语言约定的文档注释格式。

## 10. 版本控制

> **填写指南**：分支策略（主干 / Git Flow / GitHub Flow）、提交规范（Conventional Commits 或等价）、PR 流程、代码评审检查项。

### 10.1 分支策略

- 主分支：`<main / master>`
- 功能分支命名：`<feat/XX-NNNN-短描述>`
- 禁止直接推送主分支：`<是/否>`

### 10.2 提交规范

```
<type>(<scope>): <summary>

<可选正文>

<可选 footer，关联 XX-NNNN>
```

- `type` 枚举：`feat / fix / docs / refactor / test / chore / perf / build`

### 10.3 PR 评审要点

- [ ] 是否只包含本次任务范围
- [ ] 是否同步更新设计文档
- [ ] 是否补齐测试
- [ ] 是否通过 CI
- [ ] 是否避开已知反模式

## 11. 完成定义（DoD）

> **填写指南**：每个任务完成前必须满足的条件。可以配合 `14-部署文档.md` 决定是否包含「已部署到预发」。

- [ ] 功能满足需求 FR-NNN 验收
- [ ] 测试覆盖通过（见 `16-测试方案.md`）
- [ ] 文档同步更新（设计、API、数据库）
- [ ] 代码评审通过
- [ ] CI 通过
- [ ] `AGENT-GUIDE.md` 任务状态更新为 `DONE`

## 12. 文本文件格式

- 编码：UTF-8 with BOM（Markdown / 源码默认）；JSON、YAML 等现代配置按其惯例。
- 行尾：CRLF（Markdown / 源码默认）；由 `.editorconfig` 兜底。
- 空白：行尾不留空白；文件末尾保留单一换行。
